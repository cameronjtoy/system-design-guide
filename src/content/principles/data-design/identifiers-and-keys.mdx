## The problem it solves

IDs appear in URLs, APIs, logs, foreign keys, other companies' databases and analytics. Changing an ID scheme later means migrating every table that references it and every client that stored it. Common mistakes, like auto-increment IDs in public URLs or using an email address as a primary key, show up only after the system has grown.

## How it works

### Natural vs surrogate keys

- **Natural key:** a real-world value (email, username, ISBN). People change emails; usernames get renamed; "unique" real-world values turn out not to be.
- **Surrogate key:** a meaningless ID generated by the system. Use these as primary keys, and enforce uniqueness of natural values with a separate unique constraint.

### ID schemes compared

| Scheme | Example | Sortable by time | Generated without coordination | Size | Notes |
|---|---|---|---|---|---|
| Auto-increment | `48213` | Yes | No (one database) | 8 bytes | Leaks counts; hard to merge or shard |
| UUIDv4 (random) | `9f1c...` | No | Yes | 16 bytes | Random inserts scatter across B-tree indexes |
| UUIDv7 | `0190f3a2-...` | Yes | Yes | 16 bytes | Timestamp prefix plus randomness (RFC 9562) |
| Snowflake-style | `1541815603606036480` | Yes | Yes, with a worker ID | 8 bytes | Timestamp + worker ID + sequence |

**UUIDv7**, standardized in RFC 9562 (2024), is a strong default for new systems: unique without coordination, and roughly time-ordered so inserts land at the end of the index like auto-increment.

### Don't leak information through IDs

Sequential IDs in URLs reveal how many customers or orders you have and invite **enumeration**: change `/invoices/1001` to `/invoices/1002` and see someone else's invoice if authorization is missing. Random or time-ordered random IDs don't fix missing [authorization](/principles/authentication-and-authorization), but they stop casual guessing and data leaks about volume.

### Make IDs readable for humans and machines

Prefixed IDs like `cus_...`, `inv_...` (popularized by Stripe's API) tell you at a glance what kind of object an ID refers to, which helps in logs, support tickets and debugging, and lets APIs reject the wrong kind of ID early.

### IDs in other systems

- Store external IDs (from payment providers, CRMs) in their own columns with unique constraints, never as your primary key.
- Generate an **idempotency key** or client-side ID for creations so retries don't create duplicates. See [idempotency](/principles/idempotency).
- JavaScript numbers lose precision above 2⁵³, so return 64-bit IDs as strings in JSON APIs.

## Trade-offs

- **Size:** 16-byte UUIDs make indexes and foreign keys larger than 8-byte integers; usually fine, but noticeable on huge tables.
- **Time in the ID:** time-ordered IDs reveal roughly when a record was created; acceptable for most products, not for all.
- **Hot spots:** time-ordered keys put all new writes at the end of the key range, a hot spot for range-partitioned stores; hash-partition, or use a prefix, there. See [sharding](/principles/sharding-and-partitioning).

## In the real world

<Callout type="example" title="Twitter: moving off auto-increment">
When Twitter moved tweet storage away from MySQL in 2010, it needed IDs that could be generated by many machines without coordination yet still sort roughly by time. Its answer, **Snowflake**, packs a timestamp, a worker number and a sequence number into a 64-bit integer. Clients also got string versions of IDs because the numbers exceeded what JavaScript can represent exactly. Discord uses the same style of ID with its own epoch.
</Callout>

## Interview angle

<Callout type="interview">
Say what IDs you'd use and why: "UUIDv7 or Snowflake-style IDs, generated by the service, time-ordered for index locality, safe to expose." If the system is sharded, explain how the ID relates to the shard key.
</Callout>

<Callout type="tip" title="For PMs">
Anything users see (order numbers, invoice numbers, ticket IDs) may need its own human-friendly format, separate from internal IDs. Some, like invoice numbers, have legal requirements to be sequential per company, so ask finance early.
</Callout>

- Email or username as primary key.
- Auto-increment IDs in public URLs.
