## What happened

On the evening of January 31, GitLab.com was under heavy load from spam, which caused the PostgreSQL replica to fall far behind the primary. Engineers decided to rebuild replication from scratch, which meant wiping the replica's data directory and re-syncing it.

Late at night, after several failed attempts, an engineer ran the command to delete the data directory, but in a terminal session connected to the **primary** (`db1`) rather than the replica (`db2`). They noticed within a second or two and stopped it, but by then about 300 GB of production data had been removed.

## The backups that weren't

The team then turned to their backups and found that each mechanism had a problem:

- **Regular database dumps** had been failing silently, partly because of a PostgreSQL version mismatch. Failure notification emails were being rejected, so nobody noticed.
- **Disk snapshots** weren't enabled for the database servers.
- **Replication** couldn't help: the replica was the server they had just been wiping.
- **Backups to cloud storage** weren't working either: the bucket they expected to restore from was empty.

What saved them was a **manual LVM snapshot** an engineer had taken about six hours earlier, to copy data into a staging environment. Restoring from it meant losing all database changes between that snapshot and the deletion. Copying the snapshot from staging to production was slow because the staging disks were slow, which stretched the outage to around 18 hours.

GitLab livestreamed much of the recovery on YouTube and kept a public document of its progress.

## What changed

- Backups monitored and alerted on, with alerts that actually reach people.
- **Regular automated restore testing**, so a backup is only considered valid if it has been restored.
- Continuous archiving of PostgreSQL write-ahead logs to cloud storage, enabling point-in-time recovery.
- Clearer terminal prompts and runbooks so engineers can tell which host they're on.
- Recovery procedures and on-call practices reviewed, including fatigue during long incidents.

## Lessons

<Callout type="tip" title="Key takeaways">
- **A backup you haven't restored is a hope, not a backup.** Test restores on a schedule.
- **Replication is not a backup.** It faithfully copies deletions and corruption.
- **Silent failures are the dangerous ones.** Monitor that backup jobs succeed and that the resulting files are recent and the right size.
- **Make the dangerous command hard to aim wrong.** Distinct hostnames in prompts, colour-coded production shells and confirmation steps for destructive operations.
- **Transparency builds trust.** GitLab's public recovery is still cited as an example of how to communicate during an incident.
</Callout>
